# HakiOS on lapis: initial feasibility assessment

**Status: research only. No HakiOS image has been built for lapis, and nothing here is safe to flash.**

## What the reference project does

HakiOS runs a modified open-source XNU kernel and an iOS 16.5 user space. Its phone port is for the Qualcomm POCO X5 Pro (`redwood`, Snapdragon 778G); the project also has a QEMU ARM64 path. Its device-specific tree supplies a UEFI loader/port, device tree and firmware collection. The README describes it as a temporary research session loaded into RAM, not an installable ROM. It does not include Apple's iOS files, device firmware, activation credentials or keys; its documented phone workflow is Qualcomm-specific.

Sources: [HakiOS README](https://github.com/oosexgang/hackios-xnu-kernel) and [POCO X5 Pro device-port README](https://github.com/oosexgang/hackios-xnu-kernel/blob/main/devices/poco-x5-pro/README.md).

## A closer MediaTek reference

The search found [ruby-ios-bringup](https://github.com/lky005/ruby-ios-bringup), an independent XNU/iOS 16.7.16 research bring-up for the Redmi Note 12 Pro 5G (`ruby`, MT6877). Its README reports XNU reaching the lock screen and real Goodix touch on one device; GPU, Wi-Fi, USB and RTC remain unimplemented, and the project says second-device/clean-room verification remains open. Its documented boot path is stock LK → 128 MiB boot image → XNU, with UFS root storage and a framebuffer path through LK.

This is a much closer architecture reference than HakiOS's Qualcomm port, but it is not a lapis port. I cloned the public source into `reference/ruby-ios-bringup` and inspected its hardware, boot-chain, display, UFS and touch patches read-only. Important deltas from the local lapis evidence:

| Area | ruby reference | lapis |
|---|---|---|
| SoC | MT6877 | MT6878 |
| CPU | 6× Cortex-A55 | 8 CPU nodes in the candidate DTB |
| Page size | 16 KiB in its README | 4 KiB in lapis's kernel config and boot properties |
| Boot partition | 128 MiB | 64 MiB per `boot_a`/`boot_b` in the stock scatter |
| Display | 1080×2400 | 1280×2772, up to 120 Hz |
| Touch | Goodix GT9916R over SPI3 | live device reports Novatek NVT over SPI |
| Storage | UFS | UFS |

The source inspection found additional concrete deltas:

- The reference UFS host is at `0x11270000`; lapis's candidate DTB places it at `0x112b0000`. Both advertise `mediatek,mt8183-ufshci`, but a hard-coded controller address must change or become DT-driven.
- The reference shim hard-codes its RAM map, watchdog and framebuffer addresses. Its documented visible LK framebuffer is `0x7cdfc000` with stride 4352; lapis's runtime LK framebuffer is now read from the rooted runtime FDT as `0xfd72f000`, size `0x028d0000`.
- The reference touch patch bit-bangs Goodix GT9916R with Ruby-specific GPIOs and MT6360 LDOs. Lapis reports Novatek NVT; its overlay points to SPI3 at `0x11013000` and gives touch reset/IRQ pins 90 and 3. A new NVT driver and lapis power/pin sequencing are required.
- The ruby packer/documentation targets an Android v2 boot image with 2 KiB pages; lapis stock boot is v4 with 4 KiB pages. Its stock `boot` partition is 64 MiB, half the reference's 128 MiB partition.
- Ruby's notes warn that its LK has no `fastboot boot` command and its documented test path uses boot-partition writes. Lapis LK was tested with the matching stock image and also rejected `fastboot boot` as an unknown command.

The 128 MiB versus 64 MiB boot partition is a concrete image-layout blocker to copying the reference artifact. Page size, boot-header format, SoC, memory map and touch differences also need source-level work. The reference is useful as a porting guide, not as an image to flash or code to copy wholesale; review its license and upstream notices before reusing code.

## Evidence available for lapis

- The supplied stock firmware identifies the device as `lapis` and the SoC as MediaTek MT6878.
- `reference/dtb/vendor_boot_fdt_candidate.dtb` is a valid FDT v17 blob, 331,138 bytes, with root compatible `mediatek,MT6878`; it contains 1,325 nodes.
- The stock `dtbo.img` is an Android DTBO table with one overlay entry (253,381 bytes at offset 64). That overlay has 70 fragments and 504 nodes. Its fixups resolve against the candidate DTB's symbols.
- The overlay contains three possible DSI panel nodes (`p16_42_02_0a_dsc_vdo`, `p16_36_02_0b_dsc_vdo`, `p16_41_02_0c_dsc_vdo`) and both Novatek and Goodix touch-controller nodes. Runtime FDT and bound driver evidence now identify the active panel as `p16_36_02_0b_dsc_vdo`; live input and SPI binding confirm the Novatek controller.
- Read-only ADB access to the attached handset confirmed model `25080RABDG`, product `lapis_global`, Android 16, and MT6878. `getevent -lp` identified the active touch device as `NVTCapacitiveTouchScreen` with reported axes 20,480 × 44,352. Android reports the built-in display as 1280 × 2772 with 120/90/60/30 Hz modes.
- A fresh rooted property capture reports platform SDK 36, vendor SDK 34, OS3.0.309.0.WPPMIXM, active slot `_b`, and kernel `6.1.138-android14-11-g51f8c580613d-ab13911623`. These are distinct platform/vendor/kernel version identifiers; the vendor SDK difference is recorded, not independently treated as a fault. See [spi3_runtime_snapshot.md](device/spi3_runtime_snapshot.md) for this capture.
- The runtime `novatek@0` node (`novatek,NVT-ts-spi`) is on SPI3 at `0x11013000`, with 9.6 MHz maximum frequency, reset GPIO 90 and IRQ GPIO 3; `/sys/bus/spi/devices/spi3.0` is bound to the `NVT-ts` driver. The panel reset is also GPIO 90 on the same `pio` controller, so a future display/touch bring-up must handle the shared reset line carefully. The Goodix node is also present in the overlay but is not the active controller reported by Android.
- The current Android SPI-core statistics show 2,338 synchronous transfers, 935,138 TX bytes, 148,112 RX bytes, zero errors and zero timeouts; the largest nonzero size bucket is 8–16 KiB with 57 transfers. This proves the stock Android SPI/touch path is operating, but does not test XNU or identify every transfer's purpose. No SPI traffic was sent by us. Full counters are in [spi3_runtime_snapshot.md](device/spi3_runtime_snapshot.md).
- Android reports `ro.boot.flash.locked=0`, `ro.boot.vbmeta.device_state=unlocked`, and verified boot state `orange`. This is promising for later experiments but does not establish that the bootloader accepts `fastboot boot` or can launch a custom UEFI image.
- Android reports active slot suffix `_b`; the live by-name partition list confirms paired `boot_a`/`boot_b`, `vendor_boot_a`/`vendor_boot_b`, `dtbo_a`/`dtbo_b`, `init_boot_a`/`init_boot_b`, `lk_a`/`lk_b` and paired vbmeta partitions. The bootloader property itself reports `unknown`.
- With the user's approval, the phone was rebooted into fastboot for queries: `product=lapis`, `unlocked=yes`, `current-slot=b`, `is-userspace=no`, and bootloader version `lapis_3f2e32c7d_202609200804`. A test using the exact stock `boot.img` from the matching local OS3.0.309.0.WPPMIXM firmware was sent to RAM (`Sending 'boot.img' (65536 KB) OKAY`), then rejected by LK with `Booting FAILED (remote: 'unknown command')`. This confirms that the current LK does not implement the `fastboot boot` command. No partition was written. `fastboot reboot` returned the phone to Android, and ADB detected it again.
- A read-only strings scan of the supplied matching `lk.img` found a standalone `boot` token among fastboot-related strings. The runtime result above shows that this token is not evidence of a registered/working fastboot boot handler.
- Public MT6878 bootloader work exists: `MT6878-Mainline` has U-Boot patches for MT6878 and an EDK2 MediaTek tree. Its EDK2 README lists other supported devices, not lapis, so it is a research lead rather than a ready bootloader. The separate `lplk` utility targets the CMF Phone 1 and explicitly replaces that device's LK; it is not a lapis solution.
- The documented no-`fastboot boot` route in the MT6877 reference uses a repacked Android v2 `boot_a` image. Lapis is v4, has separate `init_boot`/`vendor_boot`, and has 64 MiB boot slots; its currently active slot is B. Slot A has now been read back, but its old ramdisks/AVB chain and LK version mean it is not a proven recovery or test slot. Any adapted image trial would write a boot partition and was not attempted.
- Rooted read-only hashes show active slot B's `boot`, `init_boot`, `vendor_boot` and `dtbo` match the supplied factory images byte-for-byte. Full slot A readbacks are saved under `device/slot_a_readback/`; slot A is not an exact copy of the supplied factory set. Its kernel payload and DTB/DTBO match current factory files, but its ramdisk properties identify it as the previous OS3.0.308.0.WPPMIXM build and its AVB metadata differs. Slot A bootability and AVB chain were not verified; do not treat it as a proven recovery slot. See its [readback manifest](device/slot_a_readback/README.md).
- `lk_b`'s 16 MiB raw partition copy is saved under `device/slot_b_readback/`; its first 3,595,360 bytes exactly match the supplied factory `images/lk.img`, followed by zero padding. The active B LK build string is `3f2e32c7d_202609200804`, matching the queried fastboot version. `lk_a` has a distinct older build string `3f2e32c7d_202608131223`. This is additional evidence slot A reflects an older boot-chain state, not proof it remains bootable.
- Rooted readbacks of `vbmeta_b`, `vbmeta_system_b`, and `vbmeta_vendor_b` have zero padding after their 12 KiB/4 KiB/4 KiB factory images, respectively, and match those factory files exactly. A-slot vbmeta payloads differ, although parsed headers report the same embedded public key and rollback index 0 as B. No signature or descriptor verification has been run; a matching key field alone does not prove slot A's chain is accepted.
- The normal ADB shell cannot read `/sys/firmware/fdt` or privileged chosen properties. The user confirmed root access; `adb shell su -c id` returned uid 0 in KernelSU context. A read-only capture of the live FDT now exists at `device/runtime_fdt.dtb`, and the live memory resource map at `device/runtime_iomem.txt`.
- Read-only ADB inspection of `/sys/bus/mipi-dsi/devices/1401a000.dsi0.1/driver` resolves the active panel driver to `panel-p16-36-02-0b-dsc-vdo`. The other two panel nodes remain present as alternatives in the DTBO, but are not bound to the observed DSI device.
- The matched DTBO node is `fragment@20/__overlay__/panel2@1`, compatible `p16_36_02_0b_dsc_vdo,lcm`, with `reg = 1`. It declares reset GPIO 90 and VDDI GPIO 149 through `pio`, ESD IRQ GPIO 12, and regulator references `mt6369_vtp` (`amoled-vci-supply`) and `mt6363_vcn13` (`amoled-dvdd-supply`). The overlay's Novatek touch node also declares reset GPIO 90; confirm whether this is an intentionally shared line before sequencing either device in a new boot path.
- The candidate tree describes MediaTek UFS, Mali/MTK GPU, MTK display/DSI, MTK Wi-Fi/Bluetooth, audio, USB, cameras, PMIC and other platform blocks. The extracted `fstab.mt6878` and module list are Android/MediaTek-specific.
- The HakiOS device README identifies its phone-specific XNU drivers as display, Goodix touch, UFS, Adreno 642L, WCN6750 Wi-Fi, audio DSP, modem, haptics and cameras. Its UEFI port is based on Mu-Silicium, and its SoC-address tool extracts Qualcomm-specific IPA/IPCC/AOSS/RPMh/SMMU nodes. Those drivers and address-generation logic cannot be reused for MT6878 as-is.
- No `dtc`, `fdtdump`, `simg2img`, `lpunpack`, `avbtool` or boot-image unpacker is currently available on PATH. The DTBO header and FDT structures were parsed read-only with Python; no image contents were changed.

## Stock Android boot image layout (read-only parse)

All three images are Android boot header v4 images using 4,096-byte pages. The parsed layout follows the [AOSP boot image header](https://android.googlesource.com/platform/system/tools/mkbootimg/+/refs/heads/main/include/bootimg/bootimg.h) and [boot image documentation](https://source.android.com/docs/core/architecture/bootloader/boot-image-header). The standalone `boot` image contains the GKI kernel and no ramdisk; `init_boot` contains the generic ramdisk; `vendor_boot` contains device-specific ramdisk fragments, DTB and the v4 ramdisk table, matching the [AOSP generic boot partition model](https://source.android.com/docs/core/architecture/partitions/generic-boot).

| Image | Partition-sized file | Main payload parsed | AVB footer's original image size | vbmeta at image offset |
| --- | ---: | --- | ---: | ---: |
| `boot.img` | 64 MiB | v4 kernel: 16,544,915 B; no ramdisk; 4 KiB page | `0x00fcd000` (16,568,320 B) | `0x00fcd000`, 0x980 B |
| `init_boot.img` | 8 MiB | v4 generic ramdisk: 3,132,668 B; 4 KiB page | `0x002fe000` (3,137,536 B) | `0x002fe000`, 0x340 B |
| `vendor_boot.img` | 64 MiB | v4 vendor ramdisk: 43,622,340 B; DTB: 331,202 B; two ramdisk-table entries (108 B each) | `0x029ed000` (43,962,368) | `0x029ed000`, 0x2c0 B |

Each file ends with an AVB 1.0 footer at the final 64-byte slot. The footer records the original image size and vbmeta offset/size above; the rest of each partition-sized file is padding. These values describe the stock, signed Android images only. A modified image would invalidate its existing AVB hash/signature and would need a deliberately supported verification/boot chain. In particular, the unused tail space is not automatically available for XNU, and the kernel payload must fit the image's boot protocol and LK expectations. No AVB metadata or image was changed.

## ARM platform handoff clues from the candidate DTB

The candidate DTB declares eight CPUs with PSCI enable-method: four have `capacity-dmips-mhz = 267`, and four have `1024`, indicating two performance classes. It declares an ARM GICv3 at `0x0c000000` (distributor and redistributor ranges), an ARMv8 generic timer with four PPI interrupts and a declared 13 MHz frequency, and a 1 GiB memory range beginning at `0x40000000`. The MediaTek timer block is at `0x1cc10000`; UFS is at `0x112b0000`.

The rooted runtime FDT resolves the discrepancy: it declares RAM at `0x40000000` with length `0x300000000` (12 GiB), while the extracted candidate DTB declares only 1 GiB. Thus the extracted blob is an incomplete/pre-boot candidate for memory planning; use the captured runtime FDT for further analysis. Rooted `/proc/iomem` reports 32 discontiguous `System RAM` ranges totaling 12,262,551,552 bytes (about 11.42 GiB) through `0x33fffefff`, with reserved holes and secure/modem/firmware regions. Android reports `MemTotal = 11,676,244 kB` and `CmaTotal = 229,376 kB` (224 MiB). These figures describe current Android memory ownership; a new boot chain must separately define which reserved regions it can safely reclaim. CPU affinity, secure-world ownership and whether LK will preserve this exact runtime map remain separate bring-up questions.

The live display stack confirms primary display `MTKDEV`, 1280×2772 at 120 Hz, with 90/60/30 Hz modes. The active MIPI DSI device `1401a000.dsi0.1` is bound to `panel-p16-36-02-0b-dsc-vdo`, and the live `chosen` node's `atag,videolfb` string independently names `dsi_panel_p16_36_02_0b_dsc_vdo_lcm_drv` with `lcm_panel_id = 0x10`. The runtime framebuffer base is `0xfd72f000`, size `0x028d0000` (42,795,008 bytes), covering `0xfd72f000–0xffffefff`; the matching `/reserved-memory/mblock-15-framebuffer` DT node has the same `reg`. The active panel's runtime node declares reset GPIO 90 and VDDI GPIO 149 through `pio`, ESD IRQ GPIO 12, plus `mt6369_vtp` and `mt6363_vcn13` regulators. DTB regulator constraints allow VTP 1.2–3.5 V and VCN13 0.9–1.81 V; these are permitted ranges, not measurements of the active voltage. The live Novatek touch node also uses GPIO 90 as reset, on the same `pio` phandle, so panel/touch reset sequencing must treat that line as shared.

## Lapis kernel and early-shim constraints

The stock Android v4 kernel payload begins with an LZ4 legacy stream, not gzip. Host-only decompression yielded five blocks and a 35,432,960-byte ARM64 Linux Image (`ARM\x64` magic at offset `0x38`) with kernel build `6.1.138-android14-11-g51f8c580613d-ab13911623`, `text_offset = 0`, and `image_size = 0x02270000`. Ruby's gzip repacker and image-compression assumptions cannot be reused as-is. The runtime Linux kernel resource range begins at `0x40010000`, but that does not by itself prove LK's decompression/load address for a replacement image.

The Ruby shim disables/feeds watchdog registers at `0x10007000`/`0x10007008`. Lapis's runtime DTB and `/proc/iomem` identify its MediaTek watchdog resource at `0x1c00a000–0x1c00a0ff`; Ruby's register sequence and address must not be copied. A concise hardware/boot contract is in [lapis_boot_contract.md](device/lapis_boot_contract.md).

The matching factory `vendor_boot.img` contains the active panel module. I extracted `panel-p16-36-02-0b-dsc-vdo.ko` read-only to [device/](device/panel-p16-36-02-0b-dsc-vdo.ko), SHA-256 `fa17d9db592defc31943fdac21944cc96fb86614cf456fa40c3257dad0b25015`. Its module metadata marks it GPL v2, depends on `mediatek-drm`, `mtk_panel_ext`, and `hqsysfs`, and its symbol table includes `lcm_panel_init`, `lcm_get_modes`, `panel_init_power`, and four mode objects. Host-side AArch64 disassembly plus ELF relocation parsing recovered all four mode timings (120/90/60/30 Hz) and the ordered DSI init writes; see [panel_module_analysis.md](device/panel_module_analysis.md). This is a Linux module and cannot be loaded as an XNU driver. It was not executed and no DSI commands were sent to the phone.

The live touch device is the Novatek NT38771 (`NVT-ts`) on SPI3, with 9.6 MHz maximum clock, IRQ GPIO 3, reset GPIO 90 and 16× scaled coordinates for 1280×2772. A fresh rooted `/proc/interrupts` read confirms `NVT-ts` is on `mtk-eint 3 Edge`, with SPI3 host IRQ GIC 494. I streamed the active driver module and all ten matching touch firmware/MP-test payload variants from the rooted device read-only. Static analysis of `tp_compare_ic` shows runtime `lcm_panel_id = 0x10` selects TianMa files `novatek_ts_fw_tm.bin` and `novatek_ts_mp_tm.bin`. Read-only `/proc` status confirms TianMa/NT38771 firmware `0x29` (41) and an 18×39 sensor matrix; the selected firmware image contains the matching `0x29/0xd6` version/complement pair. The runtime SPI3 pinctrl selects GPIO68=CLK, GPIO69=CSB, GPIO70=MOSI and GPIO71=MISO, function 2, corroborated by the upstream MT6878 pin-function table. The exact stock SPI host binary was extracted from the supplied `vendor_boot.img`; its `mt6989-spi` alias matches the live FDT. A public Motorola `kernel_device_modules-6.1` source candidate has the same MT6989 match and compatibility bytes, and exposes a candidate register map, though its exact revision match to Xiaomi's Android 16 build is not proven. Its extra controller-state names and GPIO6/7 settings still conflict with the child node's explicit GPIO90/3 properties, so reset/IRQ source mapping should follow the child node and live IRQ evidence, while GPIO6/7 usage remains for vendor-source reconciliation. See [touch_module_analysis.md](device/touch_module_analysis.md) and [spi_mt65xx_module_analysis.md](device/spi_mt65xx_module_analysis.md).

Xiaomi's official [kernel source index](https://github.com/MiCode/Xiaomi_Kernel_OpenSource) lists a branch named `lapis-v-oss` for “REDMI Note 15 Pro 5G” on Android V. I fetched it read-only as a shallow no-checkout reference at commit `14d48651673ff1f5f6578c793b4ae9835d349d4b` in `reference/lapis-v-oss`. Its Makefile identifies Linux 6.1.129, while this phone reports 6.1.138. The branch tree includes generic MediaTek DRM/DSI code, but no lapis-specific DTS/defconfig, no `mt6878` paths, and no source for the active `p16_36_02_0b_dsc_vdo` panel module. It is a useful source lead, but not an exact kernel match or a complete vendor kernel drop.

## Feasibility

There is no ready-to-use iOS/XNU port for lapis. `ruby-ios-bringup` is a credible starting reference because it is for a MediaTek phone, but its hard-coded boot, UFS, memory and touch assumptions do not match lapis. The first device-port blocker is now confirmed: lapis LK rejects `fastboot boot`, so the reference project's RAM-only launch path cannot be used. A lapis port needs a different boot strategy, most likely a separately developed/validated LK or U-Boot/UEFI path, or a boot-partition image workflow. Any path that writes `lk` or `boot_*` needs a separate recovery plan and explicit authorization before device changes.

## Suggested device-port milestones

1. Finish mapping `ruby-ios-bringup` CPU/GIC/timer/UFS/framebuffer assumptions to lapis DTB/DTBO and firmware. Live RAM range, reserved map, display modes, exact active panel, framebuffer and panel power dependencies are now captured; secure carveout ownership and a first-boot memory handoff remain unresolved.
2. Compare the stock v4 `boot`/`init_boot`/`vendor_boot` layouts with slot readbacks; determine whether a diagnostic kernel image can fit a 64 MiB boot slot. Slot A's boot/AVB/LK contents are captured locally; B's boot/init/vendor_boot/dtbo/vbmeta chain matches the factory files. Slot A bootability, chained AVB acceptance, and suitability of either slot for experiments remain unverified.
3. Use the now-identified `p16_36_02_0b` panel as the display reference and build a host-only v4 image-layout verifier/diagnostic shim before any device boot test.
4. If a boot-partition write is ever proposed, first verify a tested recovery path and get explicit approval. Do not overwrite `preloader`, `lk`, `nvram`, `nvdata`, or calibration partitions.
